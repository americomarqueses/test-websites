PostgreSQL Read Replica Load Balancing on GCP

This guide explains how to set up a dedicated Read-Only Load Balancer for your PostgreSQL replicas using pgpool-II. This architecture is ideal when your application logic already handles writes to the Master, and you only need a single, stable endpoint to balance and health-check your read-heavy traffic.

1. Architectural Overview

In this "Read-Only" mode, your API uses two separate connection strings:

  • Write Path (Manual): API connects directly to the Cloud SQL Primary.
  • Read Path (Load Balanced): API connects to an Internal Load Balancer (ILB), which points to a cluster of pgpool-II instances that distribute queries across your replicas.

Components

  1. Cloud SQL Replicas: Multiple PostgreSQL read-only instances.
  2. pgpool-II Layer: A Managed Instance Group (MIG) of VMs configured for load balancing only.
  3. Internal Load Balancer (ILB): Provides a single IP (e.g., 10.128.0.100) for all read queries.

2. Infrastructure Configuration

Step 1: Identify Replica IPs

Ensure your read replicas are on the same VPC.

  • Replica 1 IP: 10.128.0.6
  • Replica 2 IP: 10.128.0.7
  • Replica 3 IP: 10.128.0.8

Step 2: Configure pgpool-II for "Read-Only" Mode

When creating your Compute Engine Instance Template, use the following specialized configuration. We set the Primary weight to 0 (or exclude it) so the proxy only targets replicas.

Startup Script (Debian/Ubuntu):

#!/bin/bash
apt-get update
apt-get install -y pgpool2 postgresql-client

# Configure pgpool for Read-Only Load Balancing
cat <<EOF > /etc/pgpool2/pgpool.conf
listen_addresses = '*'
port = 5432

# Backend Replicas
backend_hostname0 = '10.128.0.6'
backend_port0 = 5432
backend_weight0 = 1
backend_flag0 = 'ALLOW_TO_FAILOVER'

backend_hostname1 = '10.128.0.7'
backend_port1 = 5432
backend_weight1 = 1
backend_flag1 = 'ALLOW_TO_FAILOVER'

# Load Balancing Settings
master_slave_mode = on
master_slave_sub_mode = 'stream'
load_balance_mode = on
replication_mode = off

# Health Check Settings (Crucial for Load Balancers)
health_check_period = 10
health_check_user = 'health_check_user'
health_check_password = 'your_password'
EOF

systemctl restart pgpool2

Step 3: Deploy the Internal Load Balancer

  1. Instance Group: Create a Managed Instance Group from the template above.
  2. Health Check: Create a TCP health check for Port 5432.
  3. ILB Setup: Create an Internal TCP Load Balancer using the Instance Group as the backend.
  4. Result: Your API now connects to the ILB IP for all SELECT operations.

3. Why use pgpool-II for just Replicas?

  1. Seamless Scaling: Add or remove replicas in Cloud SQL and update the pgpool.conf without changing API code.
  2. Automatic Failover (Read-Path): If a replica goes down, pgpool-II detects it and stops sending queries to it.
  3. Connection Pooling: pgpool-II maintains a "warm" pool of connections, reducing latency.

4. Handling Consistency (Lag)

Since you are managing writes manually, you must be aware of Replication Lag.

  • Solution A: Use pgpool's delay_threshold to automatically disable replicas that are too far behind.
  • Solution B (Application Side): After a write, perform a "Critical Read" from the Master directly for 1–2 seconds.
